### 仍存在的边界与问题

- **Gmail 应用专用密码仍受账号政策限制：**Google Workspace 管理员、高级保护或组织安全策略可能禁止应用专用密码；这需要管理员处理，程序无法绕过。
- **真实环境未验证：**Gmail/QQ/163/126 等服务的真实认证/IDLE/BODYSTRUCTURE、QQ 各版本通知标题、用户实际 Windows/代理环境仍需使用本人账号测试。合成协议测试不是端到端成功声明。
- **白名单是地址筛选，不是邮件身份认证：**精确 From 仍可能被伪造；本轮不宣称 SPF/DKIM/DMARC 验证。程序不发送邮件，不自动访问邮件链接。
- **资源有意设上限：**只取非附件正文段前 512000 字节；极长单行正文截断会丢弃未完整行，可能漏提而非误复制。BODYSTRUCTURE 深度/节点、协议行/literal/响应、HTML 正则均有限制；超限明确失败，不无界读取。
- **去重窗口有限：**已成功提交水位的记录最多保留 100 条；未提交水位凭据另行持久化，最多 4096 条，达到上限会停止推进并提示检查保存问题。跨文件夹的久远重复、UID 体系重置等不提供无限期恰好一次保证。
- **加密历史绑定用户/机器：**换机/换 Windows 用户不能直接读取；旧版本不能读取 v3 加密历史。不可解密文件保留，需恢复原用户或先将原文件移到安全位置再开始新历史。
- **当前仍是一个配置账号：**本轮落实单账号运行的正确性和安全性；多账号面板与 Gmail API 替换属于新增产品能力，未将建议变成未经验证的架构重写。后端已按账号/文件夹身份组织水位，为后续扩展避免复用状态。
- **未操作用户真实剪贴板验证：**写入顺序和清理身份已在代码层修复，但实际 Win32 交付与第三方剪贴板工具争用需实际使用验证。

### 用户可见行为变化

- 原先白名单写 `bilibili` 这种片段现在无效，应改为 `bilibili.com` 或完整邮箱；无效规则关闭邮箱接收并要求修正。

## 2. Gmail OAuth 实际使用要求

### 本机自用 / 开发测试

1. 在 Google Cloud / Google Auth Platform 创建或选择项目。
2. 配置应用名称、支持邮箱、开发者联系方式及受众；个人 Gmail 通常使用 External。测试阶段添加需要登录的 Google 账号为测试用户。
3. 创建 OAuth 客户端，类型必须是 **Desktop app**，不是 Web application、Android 或服务账号。
4. 在 Data Access 声明本程序请求的权限：`https://mail.google.com/`、`openid`、`email`。
5. 将 Desktop 客户端 ID 填入 codepass；不要把客户端密钥、授权码或令牌发到聊天中。
6. 若 Google 的该 Desktop 客户端要求 client_secret，由用户在本机配置环境变量 `CODEPASS_GOOGLE_CLIENT_SECRET`，然后重新启动 codepass。程序不把它写入源码或配置，不展示其值。
7. 在 codepass 选择 Gmail、填写完整邮箱、选择 Google OAuth 2.0，点击授权；在系统浏览器中核对应用与权限并由用户自行同意。
8. 返回 codepass 确认成功，然后开启邮箱接收。需要能访问 Google 的授权、令牌、账号信息 HTTPS 端点和 Gmail IMAP 993 端口；网络受限时检查本机代理/网络。

不使用已废弃的 OOB 手工复制授权码流程，不需要把回调暴露到公网。

### 权限与有效期

- Gmail IMAP OAuth 的权限只能使用 `https://mail.google.com/`。这是完整邮箱权限，不是只读权限；本程序执行只读 IMAP 操作，并不能将 Google 颁发的权限收窄为只读。
- External + Testing 的刷新令牌通常 **7 天过期**。这不是程序能自动绕过的限制。
- 授权可能因用户撤销、更改密码、组织管理员策略、长期不用、令牌数量上限或有期限授权而失效；需要再次授权。
- “解除本机授权”清除本地授权并停止 OAuth 接收，**不撤销 Google 端授权**。Google 端撤销应由用户在第三方应用访问权限页面执行。
- 个人自用、少量熟人使用或测试可能符合验证豁免，但仍可能有未验证警告和用户上限；不等于能不受限制地公开分发。

### 公开发布

公开应用通常需要品牌与受限权限验证：应用主页、隐私政策、联系信息、域名证明、功能演示、权限必要性解释、数据用途/存储/删除说明等。

Google 对完整邮箱权限要求充分说明必要性；对于仅提取验证码的工具，**更推荐评估 Gmail API + gmail.readonly**。gmail.readonly 仍属于受限权限，不能宣称改为它就不需验证。若受限数据经第三方服务器处理或存储，还可能需要独立安全评估；不要把这项要求泛化成所有本机应用都必须付费评估。

正式公开发布前，不建议把“注册一个测试客户端”当成完整生产上线方案。

## 3. 仍存在的高优先级问题

以下为现有邮件功能的只读审查结论，主要依据所列方法的控制流。除明确标注已处理的项目外，本轮没有把这些问题全部修复。

### 3.1 空邮箱初始化后可能漏掉第一封新邮件

**已确认，可靠性高优先级。** `windows/src/EmailWatcher.cs` 的 `RunSession` / `JunkCheckOnce` 以 water <= 0 判断未初始化。空邮箱 UIDNEXT=1 时合法水位是 0，但下一次连接又把它当未初始化，并跳到新的 UIDNEXT-1。垃圾箱每次轮询重连，尤易触发。

建议：独立初始化标志或有效身份+UIDVALIDITY；允许 0 作为已初始化水位。

### 3.2 发件人白名单并不是严格邮箱身份匹配

**仍存在的安全性高优先级问题。** `EmailWatcher.cs` 的 `MailRules.SenderAllowed` 对整个 From 做子串匹配：显示名称含可信邮箱，或恶意域名包含可信片段，都可能通过。原先“前 64 行空白导致后面规则被忽略并放行”的问题，本轮已通过统一规范化和 fail-closed 校验处理；显示名称与子串伪装的问题尚未修复。

建议：解析真正地址，明确完整邮箱/域名规则，拒绝超限规则；不要匹配显示名称。即使精确匹配，From 仍可伪造，不能宣传为发件人真实性认证。

### 3.3 QQ 弹窗直读绕过 IMAP 邮件规则

**已确认，安全性高优先级。** `QqPopupWatcher.cs` 的 `Loop` / `LooksLikeMail` 依赖进程、位置、尺寸及“邮件/邮箱/mail”等文字。它先读取候选窗口的 UIA 文字，然后判断像不像邮件；类似位置的聊天或其它窗口文字可能被误当成邮件。

直读调用 `Program.HandleEmail`，不执行邮箱主题、发件人白名单或日期规则；可能复制非邮件数字并保存部分原文。界面本轮已如实提示该风险，但识别逻辑尚未加固。

建议：默认仅作 IMAP Kick 信号；免配置直读另设明确选项，先证明是邮件通知，再读取必要内容。安全性要求高时关闭 QQ 直读。

### 3.4 临时 FETCH 拒绝后仍推进水位

**已确认，可靠性高优先级。** `EmailWatcher.cs:ProcessNew` 只将网络/TLS/对象释放等异常当作可重试。`EmailImap.cs:ReadUntilTag` 对 NO/BAD 抛出 ImapException，随后被当作单邮件问题跳过并推进 UID。

建议：区分暂时失败与确定永久问题；临时命令失败不能跳过该 UID，应退避重试。

| 垃圾箱只取第一个名称匹配目录 | `EmailWatcher.cs:FindJunkFolder`、`EmailImap.cs:ListFolders` | 多文件夹漏查；Noselect 父目录可能阻挡后续目录；literal 名称解析不足 | 保留 LIST 属性，优先 Junk，排除 Noselect，各目录独立水位 |
| 整封邮件前 512000 字节截断、未排除附件 | `EmailImap.cs:FetchFull`、MIME 正文选择 | Base64 截断解码失败；附件在前遮挡正文；附件中的旧码可能被提取 | BODYSTRUCTURE 定位非附件正文，按段限量读取，明确解码失败 |
| 去重仅保存最新一个数字与两分钟时间 | `Program.cs:HandleIncoming` | A→B→A 重复；不同发件人同码被误丢；重启或超过窗口不去重 | 使用邮件身份/Message-ID 与有限去重集合，QQ 关联独立处理 |
| 停止后仍可能发生一次副作用 | `QqPopupWatcher.cs:Loop`、`EmailWatcher.cs:ProcessOne` | 停用或换账号期间旧处理仍可能入历史、通知、复制 | 提交副作用前复核生成号；会话配置快照贯穿处理 |
| 超长数字可能被截成合法长度前缀 | `CodeExtractor.cs:Extract` | “验证码 12345678901”可能变成前 8 位；主题数字可能抢占正文真码 | 加完整数字边界；主题回退数字不要过早结束 |
| Date 缺失、解析失败、未来日期放行 | `EmailWatcher.cs:ProcessOne` | 旧邮件移入产生新 UID 或伪造 Date，可能自动复制过期码 | 用 INTERNALDATE 参考，定义异常/未来日期策略；30 分钟不是实际验证码有效期 |
| 历史保存仍非原子，部分配置字段修改未完全串行化 | `History.cs:Save`、配置字段修改处 | 历史写盘中断和静默错误仍存在；部分并发状态快照仍需完善 | Config.Save 本轮已统一锁住序列化/加密/原子落盘，OAuth 提交与解除也统一加锁；历史保存和全部状态变更需下一阶段处理 |
| 剪贴板新旧写入竞争，清理无条件 Clear | `Program.cs:StartClipboardWrite`、`ScheduleClear` | 旧码覆盖新码；清掉用户随后复制的无关内容 | 串行写入+请求号；清理核对剪贴板序列号 |

## 5. 本轮处理的集成边界与仍需验证项

- **已处理：**UI 更换服务器/账号时重置两组邮箱水位；配置导入不直接继承运行水位。后台尚无完整“账号+文件夹+UIDVALIDITY”键，旧线程与新设置的并发边界仍需进一步改进。
- **已处理：**脱敏导入仅在同一邮箱身份时保留原授权码及解密失败状态；OAuth 授权另需同客户端身份才保留。不能把旧账号凭据移用于新账号。
- **已处理：**OAuth 登录使用认证主机与身份快照；只接受 imap.gmail.com 的 Google 授权，不向自定义 IMAP 主机发送 Google 令牌。
- **已处理：**Config.Save 的序列化、DPAPI 加密及落盘全部使用同一个锁；采用同目录临时文件、Flush(true) 与原子替换，失败不截断原配置。OAuth 授权/解除提交及恢复统一同步，防止旧后台保存恢复已经解除的授权。
- **已处理：**授权保存失败使用恢复流程，恢复失败进入阻塞提示，不仅回滚内存并声称成功。
- **已处理：**每次认证使用可取消请求；停止监测会取消 Google HTTP 刷新，并在发送 XOAUTH2 前再次检查取消与生成号。此修复不代表邮件解析/历史/剪贴板提交的全部副作用屏障也已完成。
- **已处理：**失效授权明确显示“需要重新授权”，停止无效重试，并一次提示；保留原密文，不静默删除授权。重新授权成功可恢复。
- **已处理并复核：**同一失效授权的状态不会被同身份导入或设置回滚清除；不同的新授权不会继承旧失效状态。授权/解除授权完整成功后清除恢复失败标记，不再错误阻挡后续操作。本轮 OAuth 审查发现的问题均已针对性修复，真实 Google 端兼容性仍待验证。
- **已处理：**主题和发件人规则统一去空行/去重，最多 64 条、单条 256 字符、合计 8192 字符；添加、批量保存、配置导入/保存、运行匹配一致。超限拒绝而非静默截断；无效运行配置关闭邮箱接收，白名单运行校验失败拒绝邮件。主题关键词为空不接收邮件。
- **潜在可用性风险：**MIME message/rfc822 重新从递归深度 0 开始，协议行无总长度限制，超限 literal 未立即断开，HTML 正则无超时。没有进行恶意邮件攻击测试，不能称已经复现崩溃。
- **兼容性待运行验证：**QQ/TIM/QQNT 的实际通知窗口承载与 UIA 字段；.NET Framework SslStream 800ms 超时后是否可靠继续；实际 Win32 剪贴板所有权与连续写入。

## 6. 明确的隐私边界

1. `History.cs` 的 Base64 是编码，不是加密。验证码和邮件前 1000 字符能够被能读取历史文件的人恢复；DPAPI 只保护邮箱凭据/OAuth 令牌。建议正文保存可选、只保留必要字段、按年龄清理或加密历史。
2. 通知隐私模式中的局部遮罩仅替换本次识别到的 code，不保证其它恢复码、数字或敏感信息被遮住。建议默认只显示来源与固定提示。
3. 日志不直接记录邮件正文或识别数字是优点；但 IMAP 错误可能含服务端原文，尚无通用敏感信息遮罩。新 OAuth 错误不输出令牌/响应正文；既有 IMAP 日志仍需加固。
4. 应用密码的“含敏感信息导出”仍可能生成明文授权码文件；用户明确选择后才应使用，不能向他人发送。OAuth 刷新令牌本轮不导出。

## 7. 便利性、可读性与下一阶段建议

### 便利性

- 增加“测试邮箱连接”和可见连接状态：未配置、连接中、实时 IDLE、轮询、退避、需要重新授权、未找到垃圾箱，以及最后成功检查时间。
- 本轮已统一规则校验，并明确“主题关键词留空不接收邮件”。后续可增加规则匹配预览与拒绝原因，方便排障。
- 关键词标签优于一直展开的多行框；保留批量编辑给大量规则用户，并提供恢复默认与主题匹配预览。
- 邮件历史分开显示真实 From 与正文品牌，不把正文里的“【品牌】”当作已认证发件人。
- 未来需要多账号时，先建立每账号独立授权、规则、水位和状态，而不是复用当前单账号字段。

### 性能与可读性

- 水位每封保存导致整份配置重写与重复 DPAPI；可改批次提交，但须先定义崩溃重放和去重策略。
- 超过 20×200 封积压后不应直接长时间 IDLE；短暂让步后继续排空。SEARCH cap 当前只限制解析结果，非服务端返回大小。
- 解析结果应携带稳定身份、日期、来源、拒绝原因和已提取 code，避免 ProcessOne 和 HandleIncoming 重复提取与读取可变全局配置。
- 拆出清晰的认证、会话、规则、解析、提交边界；不要在修复 bug 时顺便大范围重构。
- 注释要与真实保证一致：“IDLE 失败降级”“不读取聊天”“两分钟只处理一次”等表述在加固前需收紧。

### 建议优先级

1. **发布前必须优先：**空箱水位、FETCH 重试、白名单真实地址匹配、QQ 直读边界、停止副作用屏障。
2. **随后可靠性：**邮件身份去重、IDLE 降级、附件/大邮件解析、各垃圾目录水位、历史原子保存与状态一致性、剪贴板保护。
3. **最后体验：**连接测试/状态、主题预览/默认规则、来源展示、模块可读性。
